Lesson 07 · 约 30 分钟

把游戏规则变成 Resource

这一课的胜利条件：创建 GameRules 自定义 Resource，把速度和得分规则保存为 default_rules.tres，主场景通过 Inspector 引用它。

1. Node 与 Resource 的分工

Node
Resource
有生命周期、进入 SceneTree
vs
保存数据、由节点使用
处理、绘制、物理、输入
vs
配置、素材、共享定义

例：Texture、Audio、GameRules

对 Unity 开发者而言，自定义 Resource 最接近 ScriptableObject：它是 Inspector 可编辑、可保存、可被多个对象引用的数据资产。

2. 定义 GameRules 类型

在 Script 工作区创建 res://game_rules.gd：

class_name GameRules
extends Resource

@export_group("Scoring")
@export_range(1, 100, 1) var score_per_food := 10

@export_group("Speed")
@export_range(0.05, 0.50, 0.01) var start_speed := 0.16
@export_range(0.03, 0.20, 0.005) var min_speed := 0.065
@export_range(0.0001, 0.01, 0.0001) var speed_up_per_point := 0.0015

class_name GameRules 把脚本注册为全局类型，因此它会出现在创建 Resource 的窗口，也能用于静态类型标注。

3. 创建 .tres 数据资产

  1. 等待编辑器完成脚本扫描，确认没有解析错误。
  2. 在 FileSystem 面板空白处右键，选择 New → Resource。
  3. 搜索 GameRules 并创建。
  4. 保存为 res://default_rules.tres。
  5. 双击它，在 Inspector 中观察 Scoring 和 Speed 分组。

打开文本文件会看到类似：

[gd_resource type="Resource" script_class="GameRules" ...]

[resource]
script = ExtResource("1")
score_per_food = 10
start_speed = 0.16

`.tres` 是文本 Resource，适合版本控制；Godot 自动处理序列化，无需编写 JSON 读写代码。

4. 让主场景引用规则

在 main.gd 中删除：

@export_range(0.05, 0.50, 0.01) var start_speed := 0.16
const MIN_SPEED := 0.065

换成：

@export var rules: GameRules

保存脚本，回到 main.tscn：

  1. 选中 SnakeGame。
  2. Inspector 中会出现 Rules 属性。
  3. 把 default_rules.tres 从 FileSystem 拖入 Rules。
  4. 保存场景。
先赋值再运行：未指定 Resource 时 rules == null，访问 rules.start_speed 会报错。这种明确依赖比悄悄使用错误配置更容易发现。

5. 用 Resource 替换硬编码

在 new_game() 中：

move_timer.start(rules.start_speed)

在 step_game() 的 if ate_food: 中：

score += rules.score_per_food
high_score = maxi(high_score, score)
score_changed.emit(score, high_score)
move_timer.wait_time = maxf(
    rules.min_speed,
    rules.start_speed - score * rules.speed_up_per_point
)

搜索并确认 main.gd 中不再出现独立的 start_speed、MIN_SPEED 或 score += 10。

6. 创建第二套规则

  1. 复制 default_rules.tres，命名为 fast_rules.tres。
  2. 设为：Start Speed 0.10、Min Speed 0.04、Score Per Food 25。
  3. 把主场景的 Rules 从默认版换成快速版并运行。
  4. 确认玩法变化后切回 default_rules.tres。

代码没有变化，但同一玩法获得两套数据配置。这正是数据驱动设计最小而完整的例子。

7. Resource 的共享语义

同一路径的 Resource 通常只加载一次，多个节点可能持有同一个对象引用。因此：

# 谨慎：可能修改所有引用者看到的共享配置
rules.score_per_food = 999

# 需要运行时私有副本时
var runtime_rules := rules.duplicate() as GameRules

配置 Resource 通常应当“读多写少”。玩家当前分数属于运行时状态，不应该放进共享的 GameRules。

8. 验收

  1. 项目启动无 null instance 错误。
  2. 默认规则下，每个食物仍增加 10 分。
  3. 切换快速规则后，不改代码即可改变速度和得分。
  4. main.tscn 保存了对 default_rules.tres 的引用。
  5. Remote Inspector 中可看到主节点引用的 GameRules。

9. 闭卷检索

问题 1：GameRules 为什么是 Resource，不是 Node？

它只表达可序列化配置，不需要进入 SceneTree、接收生命周期或处理绘制；实际行为由使用这些数据的节点负责。

问题 2：.tres 相比手写 JSON 有什么直接优势？

它保留 Godot 类型，自动序列化，并原生支持 Inspector、资源引用和版本控制，不必自行解析与校验字段。

问题 3：为什么不把当前 score 放进 GameRules？

GameRules 是可共享的静态规则；score 是每局独立变化的运行时状态，混入后会造成职责和共享语义混乱。
