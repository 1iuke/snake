Lesson 12 · 约 35 分钟

用证据定位问题

这一课的胜利条件：用断点解释一次蛇移动，用 Remote Inspector 找到 HUD 偏移来源，并录制一段 Profiler 基线，而不是靠猜测修改代码。

1. 四种问题，四种入口

现象
工具
回答的问题

先确定问题类别，再选择工具。到处添加 print() 或提前优化，往往只会制造更多噪音。

2. 断点：冻结一次蛇移动

  1. 打开 main.gd，找到 step_game()。
  2. 点击 var new_head := snake[0] + direction 左侧行号槽，放置红色断点。
  3. 运行游戏，等待自动停住。
  4. 在底部 Debugger 查看 Stack Frames 和 Variables。

此时记录：

snake[0]  = 当前蛇头格
direction = 当前方向
new_head  = 尚未执行或刚计算出的下一格
game_state = PLAYING

使用：

  • Step Over：执行当前行，不进入被调用函数。
  • Step Into：若当前行调用函数，进入该函数。
  • Continue：继续运行到下一断点。

观察完后移除断点，避免每次 Timer timeout 都暂停。

3. 调用栈讲述“怎么到这里”

在断点处，调用链应接近：

MoveTimer.timeout
└── _on_move_timer_timeout()
    └── step_game()

错误行回答“在哪里失败”，调用栈回答“通过哪条路径到达”。处理空引用或意外重复调用时，后者往往更重要。

4. Remote Inspector：调查 HUD 偏移

当前项目保留了一个真实待修项：main.tscn 的 Hud 实例曾保存非零 Offset。用运行时证据调查：

  1. 运行游戏并保持运行。
  2. 切回编辑器，Scene 面板选择 Remote。
  3. 展开 SnakeGame → Hud，在 Inspector 查看 Layout。
  4. 记录 Hud 的运行时 Position、Size 和四个 Offset。
  5. 切换回 Local，查看 main.tscn 的 Hud 实例覆盖值。

关键规则：Remote 中临时改值适合验证假设，但停止游戏后不会保存。确认“Offset 清零能修复”后，要回到 Local 场景修改并保存。

5. Output 与 Errors 不一样

  • print()：普通观察信息，出现在 Output。
  • push_warning()：值得注意但游戏可继续，进入 Debugger → Errors。
  • push_error()：操作失败或状态不可继续，进入 Errors 并带调用位置。
print("State changed: ", previous, " -> ", current)
push_warning("Save file is invalid; using defaults")
push_error("Could not write progress: %s" % error)

日志应回答问题，不应每帧刷屏。高频路径中的无限 print 会干扰性能和阅读。

6. Profiler：建立基线

  1. 运行游戏。
  2. 打开底部 Debugger → Profiler。
  3. 点击 Start，正常游玩约 10 秒并吃几个食物。
  4. 点击 Stop，查看 Frame Time、Physics Time 和 Script Functions。
  5. 按 Self Time 或 Total Time 排序，记录最靠前的三个脚本函数。

这个小游戏很可能没有真实瓶颈，这本身也是结论。Profiler 会带来额外开销，所以比较前后必须使用相同场景和操作。

7. Monitors：观察趋势

在 Debugger 的 Monitors 中关注：

  • FPS 与 Frame Time
  • Object Count 与 Node Count
  • Orphan Node Count
  • Memory 使用趋势

连续重开十次。如果 Node Count 一直增长且不回落，才值得怀疑实例没有释放。本项目只创建一次 Food，反复移动它，节点数应该稳定。

8. Debugger 的暂停与游戏内暂停不同

编辑器顶部的调试暂停会冻结执行，便于检查某一帧；游戏内 GameState.PAUSED 是产品逻辑，游戏仍在运行并渲染。不要把二者混为一谈。

9. 一份最小复现记录

现象：HUD 向右偏移
环境：Godot 4.7.2，main.tscn
步骤：F6 → 查看顶部标题位置
期望：左边距 60
实际：整体向右偏移
证据：Remote Hud offset_left = ...
假设：main.tscn 实例覆盖了 hud.tscn 默认布局
验证：Remote 中清零 Offset 后位置恢复

这类记录比“布局不对”更容易交给别人复现，也能防止自己重复试错。

10. 闭卷检索

问题 1：错误行和调用栈分别告诉你什么？

错误行指出失败位置；调用栈显示程序通过哪些调用路径到达该位置。

问题 2：为什么 Remote Inspector 的修复还要回到 Local 重做？

Remote 修改的是正在运行的实例，只用于验证，停止运行后不会写回场景资源。

问题 3：为什么不能看到一个循环就立即优化？

代码形状不能证明它是瓶颈；应先用 Profiler 测量实际耗时，再优化占主要成本的路径。

验收输出

完成后保留三条简短记录：

  1. 断点处一次实际的 snake head、direction、new head。
  2. Remote Hud 的 Offset，以及 Local 修复后的值。
  3. Profiler 中 Self Time 最高的脚本函数名称。
