让业务数据不再知道 ConfigFile

本课的胜利条件：ConfigFile 和 user://scores.cfg 只出现在 StorageUtility；ProgressModel 只表达进度数据与业务操作；main.gd 不再负责存档细节。

1. 三层各自知道什么

对象应该知道不应该知道
StorageUtilityConfigFile、路径、读写错误什么叫最高分
ProgressModel最高分、局数、何时保存ConfigFile 如何工作
main.gd何时吃到食物、何时结束一局存档路径和字段格式

2. 创建 StorageUtility

  1. 按 Ctrl + E 打开 QFramework 面板。
  2. 选择 创建 Utility，名称输入 Storage。
  3. 确认生成类名为 StorageUtility 后创建。

将生成脚本改为：

class_name StorageUtility extends AbstractUtility

const NAME: String = "StorageUtility"
const SAVE_PATH := "user://scores.cfg"

var _config := ConfigFile.new()

func get_utility_name() -> String:
    return NAME

func init() -> void:
    var error := _config.load(SAVE_PATH)
    if error != OK and error != ERR_FILE_NOT_FOUND:
        push_warning("Could not load progress: %s" % error_string(error))

func load_int(section: String, key: String, default_value: int = 0) -> int:
    return int(_config.get_value(section, key, default_value))

func set_int(section: String, key: String, value: int) -> void:
    _config.set_value(section, key, value)

func flush() -> Error:
    return _config.save(SAVE_PATH)

Utility 提供通用整数存储，不出现 high_score 等业务名称。

3. 注册 Utility

修改 scripts/snake_app.gd：

class_name SnakeAppArchitecture extends Architecture

func init() -> void:
    register_utility(StorageUtility.new())
    register_model(ProgressModel.new())

源码规定初始化顺序为 Utility → Model → System。因此即使它们都在 Architecture 的 init() 中登记，ProgressModel.init() 运行时 StorageUtility 已可使用。

4. 让 ProgressModel 管理自身业务

把 progress_model.gd 改为：

class_name ProgressModel extends AbstractModel

const NAME: String = "ProgressModel"
const SCORE_SECTION := "scores"
const HIGH_SCORE_KEY := "high_score"
const STATS_SECTION := "stats"
const GAMES_PLAYED_KEY := "games_played"

var high_score := 0
var games_played := 0
var _storage: StorageUtility

func get_model_name() -> String:
    return NAME

func init() -> void:
    _storage = get_utility(StorageUtility.NAME) as StorageUtility
    assert(_storage != null, "StorageUtility is not registered")
    high_score = maxi(0, _storage.load_int(SCORE_SECTION, HIGH_SCORE_KEY))
    games_played = maxi(0, _storage.load_int(STATS_SECTION, GAMES_PLAYED_KEY))

func update_high_score(candidate: int) -> void:
    high_score = maxi(high_score, candidate)

func record_completed_game(final_score: int) -> void:
    update_high_score(final_score)
    games_played += 1
    _storage.set_int(SCORE_SECTION, HIGH_SCORE_KEY, high_score)
    _storage.set_int(STATS_SECTION, GAMES_PLAYED_KEY, games_played)
    var error := _storage.flush()
    if error != OK:
        push_error("Could not save progress: %s" % error_string(error))

Model 知道字段的业务含义；Utility 知道这些字段如何落盘。以后改用 JSON，只需替换 Utility 的实现与通用 API。

5. 精简 main.gd

删除：

  • SAVE_PATH；
  • load_progress()；
  • save_progress()；
  • _ready() 中的 load_progress() 调用。

吃到食物时改为：

score += rules.score_per_food
progress_model.update_high_score(score)
score_changed.emit(score, progress_model.high_score)

finish_game() 中改为：

func finish_game() -> void:
    move_timer.stop()
    set_game_state(GameState.GAME_OVER)
    progress_model.record_completed_game(score)
    queue_redraw()

不要在 main.gd 中继续直接增加 games_played 或调用 ConfigFile。

6. 验证依赖方向

  1. 运行游戏，Remote 树应同时出现 Utility/StorageUtility 与 Model/ProgressModel。
  2. 确认启动后旧最高分被加载。
  3. 完成一局，确认局数加一；重启后数据仍在。
  4. 全局搜索 ConfigFile：业务代码中应只命中 StorageUtility。
  5. 全局搜索 scores.cfg：应只命中 StorageUtility。

7. 一个重要边界

Utility 是基础能力，不是“任何不知道放哪的代码”。例如：

  • 文件读写、随机数适配、网络客户端：可以是 Utility。
  • 加分规则、胜负判断、关卡解锁：具有业务语义，不应成为 Utility。

8. 闭卷检索

为什么 StorageUtility 不直接拥有 high_score？

Utility 负责存储技术，Model 负责业务状态；否则基础设施层会反向拥有游戏领域数据。

为什么 ProgressModel.init() 能取得 StorageUtility？

QFramework Architecture 在登记完成后，按 Utility → Model → System 的顺序挂载并初始化。

改用 JSON 时，哪些代码应尽量不变？

main.gd 和 ProgressModel 的业务逻辑应保持稳定，变化集中在存储 Utility 实现。
